## 1. ตอนนี้อยู่ตรงไหน

**ทำงานได้จริงบน staging แล้ว (ทดสอบสดแล้ว):**

- ลูกค้า: สมัคร/ล็อกอินด้วย OTP → ดูร้าน → ตะกร้า → สั่ง → จ่ายด้วย QR
  พร้อมเพย์จริงของ Stripe (โหมดทดสอบ) → แอปรู้เองว่าจ่ายแล้ว → ติดตามออเดอร์
  → ยกเลิกฟรีในช่วงที่อนุญาต → ได้รับแจ้งเตือนในแอป 12 แบบ (รวมยกเลิก/คืนเงิน)
- ค่าธรรมเนียม: ค่าส่ง ฿10 คงที่, ค่าบริการ 5% (ขั้นต่ำ ฿5 สูงสุด ฿15),
  คอมมิชชั่นร้าน 10% บันทึกตายตัวต่อออเดอร์
- ร้าน (เว็บ): ล็อกอิน, กระดานออเดอร์สด + เสียงเตือน, รับออเดอร์ + เวลาทำ,
  เมนู, เวลาเปิด-ปิด, โปรไฟล์ร้าน, โหมดปกติ/ยุ่ง/หยุดรับ
- ไรเดอร์ (แอป): เปิด-ปิดรับงาน, รับข้อเสนองาน, รับอาหาร, ส่ง, ถ่ายรูปยืนยัน
- ทีมงาน (เว็บ admin): กล่องเคสที่ต้องดูแล, คืนเงินผ่าน Stripe, ปิดเคส
- ระบบหลังบ้าน: tick ทุกนาทีบน staging (หาไรเดอร์, หมดอายุ QR/ออเดอร์ค้าง,
  แจ้งเตือน, เตือนทีมงานเมื่อร้านไม่รับใน 5 นาที/หาไรเดอร์ไม่ได้/ยกเลิกหลังจ่าย)
- บัญชี (ledger): รับเงินลูกค้า, ค่าบริการ, คอมมิชชั่น, ค่าไรเดอร์, คืนเงิน

**ยังไม่มีเลย หรือยังไม่พร้อมใช้จริง:**

| # | เรื่อง | ทำไมสำคัญ |
|---|---|---|
| G1 | **การจ่ายเงินให้ร้านและไรเดอร์ (settlement/payout)** | ไม่มีส่วนนี้ เปิดใช้เงินจริงไม่ได้ |
| G2 | **Push notification** (มือถือเด้งแจ้งเตือน) | ตอนนี้มีแค่แจ้งเตือนในแอป ไรเดอร์ต้องเปิดแอปค้างไว้ถึงจะเห็นงาน |
| G3 | **ระบบ production** (Supabase, API, เว็บร้าน, Stripe โหมดจริง, SMS OTP จริง) | มีแค่ staging/dev; เว็บร้านยังไม่ได้ขึ้นที่ไหนเลย |
| G4 | **แอปบน App Store / Play Store** | ตอนนี้รันผ่าน Expo Go เท่านั้น; Android ยังไม่เคยทดสอบ |
| G5 | **กฎหมาย/เอกสาร** (ข้อตกลงใช้งาน, นโยบายความเป็นส่วนตัว PDPA, สัญญาร้าน/ไรเดอร์, ภาษี, จดทะเบียน) | ร้านค้าแอปบังคับต้องมี privacy policy; เงินจริงต้องมีโครงสร้างที่ถูกกฎหมาย |
| G6 | **การดูแลระบบ** (Sentry, แจ้งเตือนระบบล่ม, สำรองข้อมูล) | เปิดจริงแล้วต้องรู้ทันทีเมื่อพัง |
| G7 | **ร้าน/ไรเดอร์จริง + ขั้นตอนทำงานของทีม** | ไม่มีคนใช้ก็ไม่มีโปรเจค |

## 2. หลักการวางแผน

1. **เปิดแบบนำร่อง (pilot) ให้เร็วที่สุดด้วยของที่มีอยู่** แล้วค่อยเพิ่ม —
   ไม่รอให้ทุกอย่างสมบูรณ์
2. **อะไรที่ทำมือได้ในช่วงนำร่อง ให้ทำมือก่อน** (DEC-031/032 อนุญาตไว้แล้ว)
   เช่น จ่ายเงินร้าน/ไรเดอร์ด้วยการโอนเองสัปดาห์ละครั้งจากรายงานที่ระบบออกให้
3. **ราคาค่าส่งตามระยะทาง (D-05…D-14) เลื่อนไปหลังนำร่อง** ต้องรอผลทดสอบ
   Google Routes ในพื้นที่จริงก่อน (D-16/D-17) — **ช่วงนำร่องค่าส่งแก้ได้จาก
   หลังบ้าน (DEC-070 §2)** เป็นจำนวนคงที่หรือเปอร์เซ็นต์ของค่าอาหาร เริ่มที่ ฿10
4. ทุกงานยังทำตามกฎเดิม: ทดสอบก่อน, staging ก่อน production, ไม่มีความลับใน Git,
   ไม่แต่งตัวเลข/ข้อความที่ยังไม่ได้อนุมัติ

## 8. ระบบตัวจริงบน Supabase แผนฟรี โดยไม่ให้หยุดเอง (DEC-070 §3)

### 8.1 ทำไมแผนฟรีหยุด
Supabase หยุด (pause) project แผนฟรีที่ไม่มีการใช้งานราว 7 วัน (`banhao-dev` โดน
แล้วเมื่อ 2026-11-02) — **ตรวจกฎล่าสุดบนหน้า Supabase อีกครั้งก่อนเปิดจริง**

### 8.2 วิธีกันหยุด — ไม่ใช้ออเดอร์ปลอม
ไม่สร้างออเดอร์ปลอม/ข้อมูลปลอม เพราะจะเข้า ledger, รายงานยอด และการจ่ายเงินร้าน
แทนที่ด้วย:

1. **Heartbeat ที่อ่านฐานข้อมูลจริง (สร้างแล้ว 2026-11-08):** cron `0 * * * *` ใน
   `apps/tick-worker` เรียก `GET /health` (database ping จริง) ทุกชั่วโมง แยกจาก tick
   จึงทำงานแม้ปิด tick ไว้ ไม่ต้องมีความลับ ไม่เปลี่ยนข้อมูล และ throw เมื่อฐานข้อมูล
   ไม่ ok เพื่อให้เห็นใน log ของ Worker — ตอนตั้ง production ให้ deploy worker ชุดที่ชี้ API production
2. **เมื่อเปิด tick production** (ขั้น 3.6) tick ทุกนาทีอ่าน/เขียนฐานข้อมูลอยู่แล้ว
   ก็กันหยุดได้ในตัว — heartbeat ยังเก็บไว้เป็นชั้นสำรอง
3. **เฝ้าดู:** ถ้า `/health` ตอบ `degraded` หรือเรียกไม่ได้ ให้แจ้งเตือน (อีเมล/
   Sentry) — รู้ภายในชั่วโมงเดียวถ้าฐานข้อมูลหยุด
4. **กู้คืน:** ถ้าหยุดจริง เจ้าของกด Restore บน Dashboard (เหมือน 2026-11-02)

### 8.3 ข้อจำกัดแผนฟรีที่ต้องรู้
- **จำนวน project ฟรี:** org แผนฟรีเปิดได้ 2 project พร้อมกัน — org ปัจจุบันมี
  `banhao-dev` และ `videoup` อยู่แล้ว ต้องเลือก: หยุด/ลบ `videoup`, หรือสร้าง org
  ใหม่สำหรับ production (แนะนำ org ใหม่ แยกขาดจาก dev)
- **ไม่มีสำรองข้อมูลอัตโนมัติ:** ตั้ง GitHub Actions รัน `pg_dump` ทุกคืน เข้ารหัส
  แล้วเก็บใน R2 แบบ private เก็บย้อนหลัง 14 วัน (ต้องใช้ DB password เป็น secret)
- **ขนาด:** ฐานข้อมูล 500 MB, Storage 1 GB — นำร่องพอ รูปยืนยันการส่งอยู่ R2 ไม่ใช่ Supabase
- **ไม่มี SLA** — ยอมรับได้สำหรับนำร่อง

## 9. ค่าส่งแก้ได้จากหลังบ้าน (DEC-070 §2) — ดีไซน์

### 9.1 พฤติกรรม
- 2 แบบ: **คงที่** (เช่น ฿10) หรือ **เปอร์เซ็นต์ของค่าอาหาร** (เช่น 8%) พร้อม
  ขั้นต่ำ/สูงสุดแบบไม่บังคับ — ปัดเศษระดับสตางค์ ปัดครึ่งขึ้น (เหมือนค่าบริการ)
- ค่าเริ่มต้น: คงที่ ฿10 (พฤติกรรมเดิมไม่เปลี่ยน)
- ADMIN เท่านั้นที่แก้ได้ ต้องใส่เหตุผล บันทึกผู้แก้/เวลา ใน `audit_logs`
- มีผลกับออเดอร์ที่สร้าง**หลัง**การแก้ ออเดอร์เดิมเก็บค่าส่งของตัวเองไว้แล้ว
  ลูกค้าเห็นค่าส่งจริงบนหน้า QR ก่อนจ่ายเสมอ (Checkout แสดง "คำนวณเมื่อยืนยัน")

### 9.2 ข้อมูล (migration ใหม่ — ต้องอนุมัติ)
ตาราง `delivery_fee_settings` แบบเพิ่มอย่างเดียว (แต่ละครั้งที่แก้ = แถวใหม่):
`mode` (`FIXED`/`PERCENT`), `fixed_satang`, `percent_basis_points`,
`min_satang`, `max_satang`, `reason`, `created_by`, `created_at` — แถวล่าสุดคือค่าที่ใช้
CHECK บังคับให้ค่าตรงกับแบบ, revoke จาก anon/authenticated, service_role เท่านั้น,
แถวแรก seed เป็น FIXED 1000

### 9.3 โค้ด
- `OrderPricingService.resolveOrderFees` อ่านค่าล่าสุด (ถ้าอ่านไม่ได้ → ไม่สร้างออเดอร์)
- `GET/PUT /api/v1/admin/supervisor/pricing/delivery-fee` (ADMIN)
- หน้าเว็บ admin ฟอร์มเรียบๆ แสดงค่าปัจจุบัน + ประวัติ + ตัวอย่างค่าส่งที่ค่าอาหาร ฿50/฿100/฿300

### 9.4 ผลกับบัญชี (ต้องให้เจ้าของยืนยัน — Q9)
ตอนนี้ตอนส่งสำเร็จ ระบบลง `RIDER_PAYABLE −1200` และ `PLATFORM_WRITE_OFF +200`
คงที่ (DEC-045: ค่าส่ง ฿10 < ค่าไรเดอร์ ฿12) เมื่อค่าส่งแก้ได้ ต้องเปลี่ยนเป็น:
- ค่าส่ง < ฿12 → write-off = ฿12 − ค่าส่งของออเดอร์นั้น
- ค่าส่ง = ฿12 → ไม่มี write-off
- ค่าส่ง > ฿12 → ส่วนเกินเป็นรายได้ BANHAO (`PLATFORM_REVENUE`)
ค่าไรเดอร์ยังเป็น ฿12 คงที่ตาม DEC-044
