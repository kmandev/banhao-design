Three places where this brief and the repository disagreed
1. The proposed state chain does not exist. The brief sketches ARRIVED → POD_CAPTURED → DELIVERY_CONFIRMED → COMPLETED. The deployed deliveries.state CHECK has none of those four names, and the schema is locked. The design maps POD onto the states that exist and adds none. §B.
2. "Do not commit to a schema until inspection confirms the architecture" — inspection confirms it. The column exists, the storage boundary exists, and the key-builder module names a delivery proof as its own anticipated third caller. This design therefore does commit, to what is already there.
3. There is no arrival step to design. The brief asks for a "ถึงจุดส่งแล้ว" arrival state. deliveries.state has AT_MERCHANT for the shop but no equivalent for the customer, and no endpoint would accept one. Arrival at the customer is therefore a screen state, not a server state — the rider is already EN_ROUTE and stays there until delivery is confirmed.
SECTION A
Objective, scope and design direction
OBJECTIVE
One photograph of the food at the place it was left, captured by the rider, reviewable and retakeable, and then — as a separate, deliberate act — a confirmation that completes the delivery. With cash on delivery disabled, this photo is the only evidence a handover happened at all.
IN SCOPE
Rider: the delivery-completion leg of the active-delivery screen, camera, review, confirm, and every failure between. Customer: a proof section on order detail and a completed indication on tracking. Plus the backend capabilities all of that requires, named but not built.
OUT OF SCOPE
Signatures, OTP-at-door, barcode scanning, multiple photos, video, annotation, face blurring, geofenced auto-arrival, the earlier steps of the active-delivery screen (G-7.2), and the delivery-failure path — FAILED exists in the schema but has no endpoint and no approved copy.
VISUAL DIRECTION
The Driver App redesign's language, unchanged: cream ground, one 60 px primary action, 22 px cards, mono for facts and time, state carried by fill + border + word. The camera is the single exception — a dark viewfinder is a functional requirement, so it adds a small dark-surface set, named in full below and used nowhere else in either app.

SECTION B
Delivery state-machine integration
No new state is necessary, and none is proposed. The photo is not a stage of the delivery — it is an argument the rider assembles before issuing one command. Everything between EN_ROUTE and DELIVERED happens on the rider's device, where a retake costs nothing and an abandoned attempt leaves no trace.

Abandoning at any point leaves the delivery exactly as it was. An uploaded-but-unconfirmed object is an orphan in R2 and nothing else — no row references it, no state moved. That is the same accepted orphan behaviour the menu-image and cover flows already document.
→
DELIVERED
Existing state. One new command, one transaction: verify the object exists → write proof_photo_path, state, delivered_at → move the order DELIVERING → DELIVERED.
Why not a POD_CAPTURED state
It would be a state only the rider's own device could ever cause, carrying no obligation for anyone else, and it would need a CHECK-constraint change to a locked schema. A state that nothing reads is a migration for a comment.
Why the upload is not its own endpoint pair
M-11 and M-12 use presign + a separate complete. Here the completion is the delivered command: folding them removes the state where a photo is recorded against a delivery that never completed, and the state where a delivery completes with no photo. One transaction, one authority.
Where the order state moves
Exactly as the pickup and en-route commands already do it — the delivery moves first, and only once that has genuinely happened does the order follow, through the existing unmodified orders service. DEC-018's separation is preserved.

SECTION H
Storage and access model
Conceptual model — as the schema already holds it
deliveries
 ├─ proof_photo_path  text, nullable ✓ exists
 ├─ delivered_at       timestamptz ✓ exists
 └─ state = DELIVERED  ✓ exists

delivery_status_history
 └─ EN_ROUTE → DELIVERED, actor RIDER ✓ exists
There is no POD table, and none is proposed. A delivery has at most one proof photo, so a separate row would carry a foreign key and one column. captured_at is not stored separately either — the design displays delivered_at as the confirmation time and reads the capture time from the object's own metadata, so no column is invented for it. Open decision POD-Q-03 if the Product Owner wants capture time as a first-class stored fact.
Access model
Who may create. Only the rider currently assigned to the delivery, and only while it is EN_ROUTE. Enforced the way every other rider command already is — @Roles('RIDER') plus the assigned-rider check plus a guarded conditional update whose WHERE clause carries the expected state.
Who may read. The order's customer, the restaurant's members, and platform staff on the service role. Never another rider, never anonymous. The rider who took it can see it while the delivery is theirs.
How it is read. A short-lived signed GET URL minted per request by the API, never a public URL and never the stored path. The path is meaningless without a signature, which is why the existing full-row customer SELECT on deliveries is not itself a leak.
When it becomes immutable. At confirmation. Retake is unlimited before, impossible after — a delivered delivery's proof is evidence, and evidence that can be replaced is not evidence. Note honestly: deliveries carries no column-immutability trigger, so this is an application rule, not a database guarantee. Making it one would need a migration, which is out of scope.
Retention. No mechanism exists and none is designed. The photo is personal data under PDPA — it can show a doorway, a house number, incidentally a passer-by. Q-012 gates this and is OPEN.
Object key, and why it takes this shape
deliveries/{deliveryId}/proof/{uuid}.{ext}
Server-templated from a validated UUID and an allow-listed MIME type, exactly like the two key builders that already exist. The client never supplies a key or a filename.
Not deterministic, deliberately. A retake before confirmation uploads a second object, so the key needs a component that changes — a server-generated UUID, the same choice the menu-item key already makes for the same reason. The cover-image style recompute-and-compare check is therefore unavailable here.
What replaces it is the pair the menu-item flow already relies on: a strict structural parse of the submitted key against this authorized delivery id, plus exists() proving real bytes are there. Structure narrows what shape can matter; existence proves it was used.
Orphans are accepted, as they already are for covers and menu images: a retake leaves the previous object unreferenced, and an abandoned attempt leaves one with no row pointing at it. Both are harmless and both are stated rather than swept up by a cleanup job nobody has specified.
SECTION I
Privacy, safety and accessibility
Privacy by what the UI asks for
The camera never asks for a person. Guidance names the subject — the food at the drop point — and states the exclusions in the same breath: ไม่ต้องถ่ายหน้าลูกค้า ไม่ต้องถ่ายบัตรหรือเอกสาร. No prompt, label or field anywhere in the flow requests a face, an ID, a phone number or a house number.

If a face appears anyway. The review screen exists precisely for this: retake is free and unlimited before confirmation. The review copy asks whether the drop point is clear, which is the question that also catches a person in frame. Automatic face detection or blurring is deliberately not designed — it would be a new capability, an accuracy claim, and a false sense of safety.

What the customer is never shown. No rider name, photo, phone number, plate or location. The proof card carries the image, two timestamps and one sentence of explanation.

What the rider is never shown. Nothing new. The flow adds no customer field the assigned-order read path does not already carry.
Accessibility
Targets. 82 px shutter, 60 px primary actions, 52 px secondary, 44 px floor for the camera's icon buttons — the redesign's scale, unchanged.

Contrast on the viewfinder. White on a 58%-black scrim, not on the live image, so guidance stays readable against any scene. The shutter is a white ring around a filled core so it is findable without colour.

Screen reader. The shutter is a button labelled ถ่ายรูปหลักฐาน, not "camera". The preview is an image with a label stating what it shows and when it was taken. Upload progress is a polite live region announcing percentage, not a spinner alone.

Colour is never the only signal. The green ส่งสำเร็จ CTA is also the only 20 px label on its screen and carries the word; the failure state carries an icon, a heading and a body line.

Reduce motion. The progress bar stays (it is information), the pulse and the success check's scale-in become static.

One-handed. Every primary action sits in the bottom third. Nothing important is within 16 px of a screen edge.
