M-11 — MENU MANAGEMENT
BANHAO | บ้านเฮา · design artifact for docs/design/ · design only, no implementation
Screen M-11 เมนู — the merchant surface for categories, dishes, options and daily availability. Read against the deployed catalog schema, the catalog RLS policies, the merchant API module and the shipped merchant web app at ac2c88c5 / bc6e468e. Availability is the one action designed to cost nothing; everything else is a form. In-product copy is Thai, all annotation is English.
Numbering collision, recorded not resolved. The UX specification's screen inventory calls menu management M-11 and operating hours M-12. The API repository already used those two labels for different work: restaurant-cover.controller.ts is documented as M-11 and menu-item-image.controller.ts as M-12. This artifact uses the UX-specification meaning. The implementation task numbering is a repository convention question, not a design one.

03 — AVAILABILITY
One tap, no dialog, and it must survive being wrong
The UX specification is explicit: “ปิดขายวันนี้ on an item is inline, immediate and reversible, with no dialog — it is the single most frequent merchant action during service and must cost nothing.” The switch therefore writes optimistically and reverts on failure, exactly as useOrderActions already handles a failed transition on the board. There is no second availability model to reconcile: is_available is the whole state, and 20260817000001 confirmed a sold-out dish stays visible to customers as วันนี้หมด.

04 — STATE B · CREATE & EDIT
One drawer, two modes, distinguished only by its title and its footer
The form reuses M-04's 520px right drawer, scrim and focus trap rather than a new overlay paradigm. Create opens empty with พร้อมขาย preset on (matching is_available default true); edit opens prefilled. Escape and ยกเลิก both close, and both raise the discard dialog once the form is dirty. Save is disabled until the form is both valid and dirty, so a merchant who opened a dish to look at it cannot write an identical row.

06 — OPTION GROUPS
min_select / max_select is shown as a rule, not as two numbers
The schema stores min_select and max_select precisely so that BQ-009 (single- vs multi-select) stays data rather than schema. A merchant should not be asked to encode that as arithmetic, so the editor offers the three shapes that map onto the pairs the customer app can already render, and writes the numbers underneath. The preset vocabulary is an interpretation and is listed in §14.

Rename and reorder are safe; retiring a category is not

08 — REMOVAL
The copy may not promise deletion, because the database refuses it
menu_items_reject_delete raises on any DELETE, and order_items.menu_item_id is on delete set null precisely so history keeps pointing at a real row. Removal is therefore an archive — archived_at set — and the dialog says so in the same register the UX specification already applied to addresses: copy must not promise removal. Both destructive paths carry a dialog; availability does not.

10 — RESPONSIVE
Below 768px the row breaks in two and the drawer becomes a sheet
The merchant web app is a Next.js app used on a shop tablet and, occasionally, a phone. The overview keeps the same information at every width; only its arrangement changes. Price and the availability switch stay on one line together because they are the two things a merchant checks mid-service, and the switch keeps its 44px target at every width.

14 — IMPLEMENTATION CONSTRAINTS
M-11 cannot be built without new write endpoints
This is the artifact's single most important finding. 20260811000003 revokes every privilege on all five catalog tables from anon and authenticated, and 20260811000011 grants back select only. A merchant client physically cannot write a dish, a price or an availability flag. The only merchant catalog endpoints that exist are the two image-upload routes. Everything designed above therefore waits on API work that is not performed here.
