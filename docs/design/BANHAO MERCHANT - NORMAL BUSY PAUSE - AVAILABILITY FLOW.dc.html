2. Busy has nowhere to live, and Pause has no status value. restaurants.status is CHECK-constrained to DRAFT · PENDING_APPROVAL · ACTIVE · SUSPENDED · CLOSED — no PAUSED, no BUSY — and no column on any table expresses a busy mode or a busy preparation time. 01 — PRODUCT INTENT
A busy kitchen has one honest option today: stop taking orders. Busy exists so it has a second one.
Without a middle setting, a merchant with a full pass either accepts orders they cannot cook on time or closes the shop and loses the evening. Both outcomes are bad, and the second one is worse for the platform than for the merchant. Busy keeps the shop open and moves the cost onto the estimate the customer agrees to before ordering — which is the only place that cost can honestly sit.

WHY PAUSE IS NOT DRAWN AS A STATUS VALUE — six load-bearing readers of status = 'ACTIVE'
{{ r.where }}
{{ r.effect }}
Enumerated in the decision pack as Candidate A's impact, and every consequence but the first contradicts a requirement in this brief: customers must keep seeing the shop, must keep browsing the menu, and existing orders must be unaffected. A PAUSED status produces a shop whose menu nobody can load. Candidate B's consequence matches what a pause means far better — the storefront closes while menu and hours stay readable — but selecting it belongs to the Product Owner and to BQ-007, so this design describes the shape without choosing it.
The option this design rejects, and why. Busy could be implemented with no migration by overwriting restaurants.avg_prep_minutes with a higher number and restoring it on return to Normal. Do not. That column is catalogue data, it is what a restaurant's normal prep time is, and a crash between "set busy" and "restore normal" leaves the restaurant permanently claiming a busy estimate with nothing recording that it was temporary. A mode needs a field that says which mode it is; borrowing a value field to imply a mode is how a system loses the ability to answer "was this restaurant busy last Tuesday". Recorded as AV-D01.

06 — PREPARATION TIME BEHAVIOUR
An order's estimate is decided once, when the order is created, and never revised by a mode change.
This is not a rule the UI enforces — it falls out of the architecture. V1.1 § 19 specifies POST /orders with full snapshotting, and create_order() already snapshots prices and options at creation. An estimate captured the same way cannot be retroactively changed by a later mode switch, because nothing reads the restaurant's current mode after creation.

One unavoidable collision with M-05. M-05 already gives the merchant a required prep-time choice at the moment they accept each order — and M-05's own finding was that no column on orders carries per-order prep time and POST /orders/:id/accept has no DTO. Busy's prep time and M-05's per-order prep time are the same quantity chosen at two different moments. Two coherent readings exist and design cannot pick: Busy sets the default the accept dialog opens with (merchant can still override per order), or Busy replaces the per-order choice while active. Recorded as AV-Q01 — it changes both the accept dialog and the command signature.

08 — CUSTOMER-FACING BEHAVIOUR
Busy is a longer wait, stated up front. Pause is a temporary closure, and the copy has to say temporary.
No new customer screen is proposed. Every touchpoint below is a state on a screen the customer app already has, which is the correct scope for an availability mode — and it keeps the UX specification's existing closed-shop vocabulary intact rather than adding a competing one.

The checkout race is the one that costs money. A customer can be on the payment screen when the merchant pauses. Phase D already built the answer and it is the only correct one: POST /api/v1/cart/validate runs on the place-order press, not on mount, and fails closed — navigation only follows a successful validation. Availability must be one more named 409 alongside PRICE_CHANGED / ITEM_UNAVAILABLE / MIXED_RESTAURANT, rendered in the same conflict pattern the checkout screen already has. Do not build a second mechanism, and never block only in the client — a client that decides a restaurant is open is the same class of mistake CON-002 forbids for payments.
09 — FAILURE, CONCURRENCY & STALE STATE
The pill shows what the server confirmed. Never what the merchant just tapped.
Optimistic mode switching is tempting and wrong here: a merchant who believes they are paused while the server has them open will get orders they refuse to cook. The pill is server truth, the dialog holds the in-flight state, and a failed request leaves the previous mode visibly intact.

NEVER IN THE MERCHANT UI
No merchant-facing control may perform, request, approve or acknowledge an L4 operator action. No "ขออนุมัติ" button, no supervisor case reference, no visibility into who proposed a pause. A merchant sees their own availability and nothing about the operations queue that may be discussing them.
And a supervisor-initiated pause is not presented to the merchant as their own Pause mode. If the two mechanisms end up writing the same field, the merchant-facing copy must still distinguish "you paused this" from "the platform paused this" — otherwise Resume looks available when it is not. Recorded as AV-Q02.
AUTO-PAUSE — RESERVED SPACE ONLY
The mode card reserves one line for a future automatic pause, worded as a possibility with its dependency named: ระบบอาจหยุดรับออเดอร์อัตโนมัติตามนโยบายที่กำหนด · BQ-013 OPEN. That is the entire treatment.
No threshold, no count, no window, no duration, no cooldown, and no example. The earlier "three misses → thirty minutes, twenty-four hour cooldown" figures are not approved policy and appear nowhere in this package. Auto-pause also does not get a merchant-facing control — it is a system transition (AV-T6) whose consequence design belongs to BQ-013, not here.
