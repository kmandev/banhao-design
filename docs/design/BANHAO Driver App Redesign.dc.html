UX problems this redesign fixes
1. Status is a strip; the control that changes it is a separate button further down. Two glances for one fact.
2. The offer card's largest element is a round number. The only time-critical value — the 60-second window — is rendered as an absolute timestamp the rider has to subtract from the clock.
3. Nothing distinguishes a live offer from a listed-but-expired one, even though expired offers genuinely appear in the list.
4. Errors are one line of red body text at the top of a scroll view; a rider who has scrolled never sees it.
5. Body copy is 14–15px. Outdoors, at arm's length, in sun, on a bike.
6. White on #E4572E measures 3.68:1 — below AA for the 15px button label in use.
What must not move, and why
Polling semantics. Fetch on focus · 15 s interval while focused · timer cleared on blur · immediate fetch on refocus · post-action re-read coalesced by refreshPending. Tests E, M, N, O, P, Q are exactly this.
Server authority. No optimistic accept, no local list patching, no client-side expiry gate. The card is re-read from the server after every action.
The approval gate. A non-approved rider gets a tree with no toggle in it — absent, not disabled (DEC-UX-006).
Position before flag. Going online is capture → POST location → set is_online. Any failure leaves the rider offline and says why.
SECTION A
Design overview
CONCEPT
One fact, one action, per screen
Each screen answers a single question in its largest element and offers exactly one control to change the answer. Home answers am I receiving work. The inbox answers how long do I have. Nothing else competes for the first glance.
PHILOSOPHY
The screen never knows better than the server
A countdown that hits zero does not disable รับงาน; the rider taps and the API says OFFER_EXPIRED. A tap never moves a card by itself — the list is re-read. Silence is drawn as silence, never as calm.
VISUAL DIRECTION
Operational, not decorative
The customer app's warm cream and orange, turned up for daylight: one saturated accent used only for the primary action, state carried by a filled surface plus a border plus a word — never by hue alone. No gradient, no shadow that isn't separating a layer, no illustration.
INFORMATION HIERARCHY
Time · state · identity · detail
Perishable values are biggest: the countdown, then the online state. Identity (round number, offer id) is mono, small, and never competes. Absent data is stated in words rather than filled with a placeholder.

Touch targets and spacing
60 px — the one primary action on a screen (เปิดรับงาน, รับงาน). Above the 44 pt baseline because it is pressed with a glove, on a bike stand, in a hurry.
56 px — secondary and destructive-adjacent controls, inputs, retry.

Contrast findings — acted on
White on #E4572E = 3.68:1
Fails AA for the 15px semibold button label the shared Button ships. Already recorded as UX-FINDING-02 against Design System v1.0.
White on #C2431F = 5.07:1
Passes AA at every size. It is already a token (colors.primaryPressed), so the driver app adopts it as its resting primary fill and darkens the pressed state one step. No new colour enters the system.
#9A8C7E on cream = 3.06:1. Decorative only (UX-Q-001). The driver app never uses it for a value the rider must read — only for the privacy note and captions.
The other measured pairs. state.dangerText #B23030 on cream = 5.9:1, which is why error headlines do not use state.danger #D93A3A (4.3:1 — passes AA for body, but not with headline weight over a tinted surface). onSuccess.text #0A5C3F on #E7F4EE = 7.4:1. text.secondary #4A4038 on cream = 9.3:1, against 4.6:1 for the #7A6E64 it replaces.

THE FOUR THINGS THAT WOULD BREAK ACCEPTANCE
1. Disabling รับงาน / ปฏิเสธ when a countdown reaches zero — breaks I, and puts the client ahead of the server.
2. Removing an acted-on card locally instead of re-reading the list — breaks M and hides the real outcome of H.
3. Adding a second timer, a background task, or Realtime to the inbox — breaks N, O, P and crosses TQ-002, which is still OPEN.
4. Rendering a disabled toggle for a non-approved rider instead of no toggle — breaks B and contradicts DEC-UX-006.

Animation guidance
Four movements, and no fifth. Online dot — 1.8 s opacity pulse, the only ambient motion in the app, and it means "the timer is alive". Countdown — a 1 s tick on the mono digits and a linear progress bar; no easing, no bounce. Card enter — 160 ms fade + 8 px rise when a poll adds an offer, so a new card is noticed without the list jumping. Toast — 180 ms slide from the bottom inset, 4 s hold, 140 ms out. Everything else is instant. Honour AccessibilityInfo.isReduceMotionEnabled: the pulse becomes a static dot, the card enter becomes an opacity step.
Accessibility
Every control keeps accessibilityRole="button" and the accessibilityState pair the shared Button already sets. The countdown gets accessibilityLiveRegion="polite" with an accessibilityLabel of "เหลือเวลารับงาน 41 วินาที" — never the bare digits. State is never colour alone: the online card carries a word, a dot, a fill and a border. Text scales to 200% without truncation — no fixed-height text container in any frame above. All existing testID values are preserved verbatim; the acceptance suite selects on them.

SECTION I
DRIVER_APP_DESIGN_REPORT
Screens designed
13 frames across 6 routes: Login · Otp (valid + invalid) · Status (pending, blocked) · Home (offline, online-with-offers, going-online busy/failed, profile error) · Offer inbox (empty, one live offer, multiple with one busy, expired + conflict toast, load error + offline banner) · Active delivery scope marker. No new route is proposed.
Backend dependencies
Reads: riders · rider_availability · rider_assignment_attempts, all direct-to-Supabase under existing RLS. Writes: rider_availability.is_online (column-scoped grant), POST /rider/location, POST /rider/offers/:id/accept, …/decline. The redesign needs nothing that does not already exist.
Retained vs replaced
Retained unchanged: all four hooks, all seven repositories, both navigators, Screen, every Thai action-error string, every testID, the whole auth flow's logic. Replaced: StatusStrip → StateCard; the inline offer card → OfferCard + Countdown; inline red error text → Toast; ad-hoc centred views → EmptyState / ErrorState. Emoji glyphs are carried over unchanged — the frames above use them exactly as StatusStrip and Splash ship them today. They are stand-ins, not a decision: see the icon-set item opposite.
Open questions this design does not answer
The icon set. Every glyph in §C is an emoji, carried over from the current StatusStrip and Splash. Emoji are not brand assets and render differently on every Android OEM, so a rider on one handset sees a different mark from a rider on another. No repository document specifies an icon set for this app, and this design does not invent one — the frames keep the glyphs that ship today and flag the choice. Deciding it is a small, separate piece of design work.
DQ-G7-01 — which strip variant DOCUMENTS_REJECTED wears; the redesign keeps the interim mapping. DQ-G7-02 — whether the inbox may state its 15-second cadence in copy; the frames do, and this needs UX sign-off. DQ-G7-03 — position staleness; presence only, absolute timestamps. BQ-029 — every rider money number. BQ-022 — onboarding, which is why no Status screen offers an action. TQ-002 — push versus polling.
IMPLEMENTATION READINESS
READY
Every screen in §C is buildable against the read and write paths that exist at the inspected commit, with no schema, RLS, API, endpoint or business-rule change. The 16 new token values in §D are additive and fully enumerated, so no colour has to be decided during implementation. Four things are conditional rather than blocking: the offer count on Home (DG-05) needs a focus-only read to be approved as within polling policy; the 15-second cadence copy (DQ-G7-02) needs UX sign-off; the icon set is undecided and the frames carry today's emoji as stand-ins; and the active-delivery flow (DG-04) stays out of scope until G-7.2 has a completion endpoint and a delivery-state read path. None of the four blocks any frame drawn above.
