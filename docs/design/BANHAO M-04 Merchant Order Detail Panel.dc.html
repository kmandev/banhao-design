BELOW 768px — IMPLEMENTATION TRADE-OFF
The board already treats the tablet layout as its floor (M-2.6 §07, "NOT DECIDED… a safety net, not a proposed mobile workflow"). The panel follows: below 768px the drawer's max-width:88% simply resolves smaller, becoming an almost-full-width sheet over the board. No sheet component, no route, no second information architecture. Recorded as a trade-off, not a design for phones.
05 — PANEL STATES
Loading, failure, and absent data are three different pictures
The skeleton is the panel's own hierarchy greyed out, not a generic block — a merchant should recognise where the items will be before they arrive. The failure state is a panel-local alert that leaves the board fully usable behind it, and never offers a destructive way out.

06 — INTERACTION & ACCESSIBILITY
Opening a detail must never cost an accept
The card's primary action button is the one thing the panel must not swallow. The card body becomes the open affordance; the button keeps its own click and stops propagation, so a merchant pressing รับออเดอร์ in a hurry never gets a panel instead.

07 — REALTIME & STALENESS
One subscription, and it is the board's
The panel subscribes to nothing, polls nothing and owns no timer. It reads the selected order out of the board's live array by id, so its header state chip is always the board's state — the same value, one render behind nothing. Everything the panel fetches for itself is immutable by database trigger: order_items and order_item_options reject UPDATE and DELETE outright, and every money and snapshot column on orders is immutable for the service role too. There is nothing there to keep in sync.
{{ r.event }}
{{ r.behaviour }}
Why the history refetch is event-driven and not a subscription. order_status_history is deliberately absent from the supabase_realtime publication — migration 20260831000001 says so in as many words, and defers the question to "the future order detail panel". M-04 does not need it: the board's existing orders UPDATE event is the same event that appended the history row, in the same transaction. Reacting to the state change the panel already sees costs one query and no new publication member, so this design does not ask for that migration.
