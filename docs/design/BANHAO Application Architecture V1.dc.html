Two tracks run in parallel
After MERCHANT_ACCEPTED the kitchen and the rider search proceed in two separate domains; a merchant never waits for a rider before starting to cook. PICKED_UP is the join point: it requires both READY_FOR_PICKUP in the order domain and an assigned rider in the delivery domain. Either may arrive first, and neither blocks the other.
Five exception states sit in the CHECK — build none of them yet
Their names are still PROPOSED and four policies remain OPEN (BQ-013, BQ-015, BQ-016, BQ-017). Building against an unapproved name means a later rename touches the transition table, history rows already written to production, copy in four apps, and every test. A failed payment simply leaves the order in PENDING_PAYMENT, which DEC-019 permits and the customer app already renders.
05 — MONEY
Payment, ledger, and idempotency
Every table in both domains is API-only, and a signature-verified webhook is the only path to SUCCESS or REFUNDED. Ingest and processing are separate transactions, so a crash mid-flight can never erase the evidence that an event arrived.
OPERATION
IDEMPOTENCY KEY
{{ i.op }}
{{ i.key }}
Natural keys first; idempotency_records only where no natural key exists (ADR-004).
A duplicate webhook and a duplicate payment are different things
A repeated provider_event_id violates a unique constraint; the handler reads back the stored outcome and returns 200 so the provider stops retrying. A second successful transaction against an already-SUCCESS payment is something else entirely: it is real money, it is recorded in payment_transactions, and it becomes a refund obligation. Never swallow it as a duplicate.
The ledger has no zero-sum trigger — deliberately
CON-003 still binds; DEC-034 only moved where it is enforced. The service asserts that each group sums to zero inside the transaction and aborts if it does not, and scheduled reconciliation re-verifies afterwards. A correction is a reversing entry in a new group, never an edit. Do not add a trigger.

Riders have exactly one read path, and it must not be widened
Riders hold no policy on orders, order_items or order_item_options — those policies were dropped and replaced by three column-scoped views with security_barrier = true. The barrier is required, not cosmetic: without it the planner may evaluate a rider-supplied predicate before the row check, turning query errors into an oracle for rows the rider may not see. That was proven by execution, not by reasoning. The application's obligations are: never re-add a rider policy to the base tables, never select * in rider context, and give @banhao/types a distinct RiderOrderView type so the type system enforces the boundary the views enforce.
07 — COST
$0/month is a target, not a guarantee
V1 is designed to operate within free tiers where realistically possible. Actual cost depends on traffic, provider pricing, and free-tier limits — all outside this architecture's control. One line is not free regardless: SMS OTP, roughly $2/month, plus unavoidable store fees at launch.
