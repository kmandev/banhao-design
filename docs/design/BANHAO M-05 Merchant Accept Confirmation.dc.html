M-05 — ACCEPT CONFIRMATION
BANHAO | บ้านเฮา · design artifact for docs/design/ · design only, no implementation
Screen M-05 ยืนยันรับออเดอร์ (พร้อมเวลาทำอาหาร) — the confirmation step that opens when a merchant presses รับออเดอร์ on an M-2.6 board card, and closes by issuing the existing accept command. Read against the shipped merchant app, the orders module and the deployed schema at ac2c88c5. M-05 introduces no order state, no new endpoint, no new navigation and no notification system. It does require one contract extension and one schema field, both documented in §14 as constraints for implementation — not performed here. In-product copy is Thai; all annotation is English.

00 — SCOPE
One decision, taken before the command is sent
M-05 is a step inside an existing flow, not a screen a merchant navigates to. It sits between the press of รับออเดอร์ and useOrderActions.runAction(order, 'accept'), and its only product job is to make the merchant name a preparation time before the order leaves the ออเดอร์ใหม่ column.

02 — STATE A
Desktop · ≥1024px · centred dialog over the board
M-05 is a modal dialog, 480px, centred — the smallest overlay that can own the keyboard for a required choice. It reuses M-04's scrim (rgba(31,26,22,.32)), focus trap and Escape behaviour verbatim, and no other overlay paradigm is introduced. It is not the M-04 drawer: the drawer is a reading surface a merchant leaves open while the board keeps moving, and this is a two-second decision that must not be left open. The originating card keeps the 2px orange ring so the dialog's subject is unambiguous, and the board behind it stays legible so an arriving order is still visible.

03 — STATE B
Tablet · 768–1024px · same dialog, thumb-sized
Same component, three parameter changes: the dialog is min(92vw, 560px), every target rises to the board's existing tablet height (--banhao-action-height: 56px, and 64px for the presets so a chip is never smaller than the button that opened it), and the five presets wrap to a 3+2 grid rather than shrinking to 60px-wide taps. The dialog is not converted to a bottom sheet: a sheet costs vertical travel from a merchant's hand to the primary action, and the board's own tablet layout is two columns plus a tray, so a centred dialog stays clear of the tray.

05 — CONFIRMATION, LOADING, FAILURE
Four states of the same dialog
The dialog stays mounted through the whole mutation. It does not close optimistically, it does not report success itself, and a failure leaves it open with the merchant's selection intact — the retry is the same button, pressed again.

06 — THE 3-MINUTE ACCEPT WINDOW
Four phases, one existing function
The phases come from acceptWindowState(placedAt, now) as already shipped — MERCHANT_ACCEPT_WINDOW_SECONDS = 180, warning at ≤ 60s, expired at 0. M-05 renders the same three values in a dialog-scale strip and adds no timer of its own. BQ-013 is untouched: nothing here auto-rejects, auto-refunds, cancels, or decides what happens at 3:00 — the strip only reports the clock the board already shows.

Expiry while the dialog is open
If the window reaches 0 with M-05 open, the dialog switches to the expired body in place: the preset group and the confirm button are removed (not merely disabled — there is nothing to confirm), the existing board copy หมดเวลาตอบรับ · ติดต่อผู้ดูแลระบบ is shown verbatim, and the only remaining control is ปิด. Focus moves to that button and the change is announced. An accept already in flight when the clock hits 0 is not cancelled client-side: the server's guarded WHERE state = 'PAID' is the only authority on whether it lands, and BQ-013 has not defined an expiry rule for the server to enforce.

The radio group is one tab stop, not five: Tab enters it at the checked option (or the first option when none is checked), arrow keys move and select within it, and Tab leaves. 09 — RIDER VISIBILITY
Deferred, and stated as deferred
M05-DEFER-01 — RIDER PREP-TIME VISIBILITY
Prep time would plainly be useful to a rider deciding when to leave for the shop, and the natural home is the existing job surface fed by rider_order_view — the same view that already projects o.accepted_at. It is not designed here, for one concrete reason: exposing the field to riders means adding a column to a deployed database view, which is a migration, and the database is LOCKED at 16/16. There is no rider surface that can display the value today without one.
Decision: future integration. No rider screen, no rider copy, no rider navigation, and no rider state transition is designed or implied by M-05. When the per-order prep field lands (§14), a one-line follow-up can add it to rider_order_view and to the existing job card — but that is a separate brief with its own product decision about whether a rider should see an estimate that may already be stale.
