### Judgement calls worth recording

**Existing code was reviewed before designing, and largely kept.** The brief
said not to blindly redesign working code, and `PaymentProvider` turned out to
already encode CON-002, DEC-028 and DEC-018 correctly — explicit `idempotencyKey`
on every operation, `verifyWebhookSignature` as a required capability, nothing
returning an order status. It is retained verbatim; the architecture adds only
the ingest/process split around it. Same for the two-client `SupabaseService`
and the module rules.

**ADRs are a separate namespace from DEC, with an explicit precedence rule.**
The brief said not to mix them. Beyond separating the files, the ADR document
states that a `DEC` beats an `ADR` and that a conflict means the ADR is a bug —
otherwise a future agent could "resolve" a contradiction the wrong way.
Product/stack decisions already recorded (DEC-009/010/011/013/014/015/018/020/
028/030) are listed as **inherited constraints, not re-recorded as ADRs**, so no
decision gets two homes.

**Every ADR is `PROPOSED`.** No human has approved the architecture, and
`ai/DEVELOPMENT_RULES.md` forbids an agent marking a decision `ACCEPTED`.

**"NestJS writes, clients read" was chosen over RLS-enforced business rules.**
RLS expresses "you may only see your own rows" well; it cannot express "only if
payment is `SUCCESS` and the caller owns the restaurant and the 3-minute window
has not expired". Splitting a state machine between policies and TypeScript
would violate the brief's own §4 (rules must not scatter) and would be
especially bad for an AI-maintained codebase, where a rule that is not in one
findable place effectively does not exist.

**The queue decision was justified rather than assumed**, as §3 required.
Postgres + `FOR UPDATE SKIP LOCKED` at roughly one job per minute, behind a
`JobQueue` interface, with numeric revisit triggers written down so the review
happens on evidence. The deciding argument was not cost: **a job can be enqueued
in the same transaction as the state change that causes it**, which an external
broker cannot do, and that is the same dual-write problem the outbox exists to
remove.

**Money rounding was designed to make CON-003 true by construction.** Rather
than computing each component independently and reconciling, the residual
component is derived by subtraction, so the four ledger lines sum to exactly the
amount received for any rate and any rounding rule. No rate was chosen —
DEC-023/024/025 keep every number open.

### Findings

- **`Satang` is an unbranded `number` alias** in `packages/types/src/money.ts`,
  so `bahtToSatang`'s input and output are the same type to the compiler.
  Recommended branding (ADR-007). Not changed — no code in this step.
- **`refund()` on `PaymentProvider` is currently unsatisfiable.** Q-020 found no
  provider supports native PromptPay refunds, and DEC-016 removed the
  cash-refund fallback. If Q-020 resolves to an out-of-band mechanism, refund
  should move off `PaymentProvider` rather than remain a lie in the interface
  (TQ-008).
- **Two of the three T0 blockers are not about the payment provider.** TQ-011
  (migration workflow) is cheaper to agree before the first domain migration
  than to retrofit across schema written by several agents. TQ-012 (proving the
  rider race is safe) matters because a `SELECT`-then-`UPDATE` refactor would
  silently reintroduce the race and a mocked unit test would not catch it — the
  EVENT-007 precedent of verifying by execution against real PostgreSQL is the
  right standard.

## Architecture final review (same day)

Reviewed `feature/technical-architecture-v1` against the business record before
allowing database/backend work. **Review only** — no code, no migration, no
business-model change. Verdict: **PASS WITH FINDINGS**, 7 findings, all fixed on
the same branch.

Reviewing my own architecture required reading it adversarially rather than
confirming it. The most valuable finding came from tracing an interaction I had
not walked end to end: the backstop unique index I added to protect DEC-020's
rider race turns out to **block DEC-021's reassignment**, because the departing
rider's `rider_assignment` stays `ACCEPTED` and `delivery.rider_id` stays set.
Two mechanisms that were each individually correct combined into a deadlock.
That is exactly the class of bug that is cheap now and expensive after a
migration exists.

Findings and fixes are recorded in EVENT-015. Nothing required Product Owner
input, so no new `BQ` was raised; TQ-012 absorbed the testable invariants.

## Supabase Database Design v1 (EVENT-016)

**Branch:** `feature/database-design-v1`, from `feature/technical-architecture-v1`.
**Output:** `docs/DATABASE_DESIGN.md` + `docs/OPEN_DATABASE_QUESTIONS.md`.
⛔ **No migration, no SQL executed, live Supabase untouched.**

### What was done

Read the business and architecture record, then **read the three applied
migrations line by line** before designing anything. That was the highest-value
step: `20260809000003_harden_profiles_rls.sql` contains a five-step security
pattern that generalises to every table, and its own comments explain *why* each
step exists. Reusing it beat inventing a new convention.

### Judgement calls worth recording

**`revoke` before `grant`, always.** Supabase grants `ALL` on public tables to
`anon`/`authenticated` by default. A migration that only adds RLS policies still
leaves table-level write privileges in place. Migration 3 discovered this the
hard way (phone was client-writable); the design now makes revoke-first step one
for every table.

**Composite foreign keys to enforce DEC-017.** `cart_items` carries a
denormalised `restaurant_id` and two composite FKs — to `carts (id,
restaurant_id)` and `menu_items (id, restaurant_id)`. They share the column, so
they must agree, and a cross-restaurant cart becomes unstorable. Chosen over a
`BEFORE INSERT` trigger because a trigger is invisible in the table definition
and every future agent has to re-derive it; a constraint is self-documenting.

**`text` + `CHECK` over enums for state columns.** The deciding evidence is
project history rather than theory: the order vocabulary **already changed once**
(DEC-019 superseded the 12-state machine) and five exception names are still
`PROPOSED`. Enum value removal is a type migration; a CHECK is one line. The
live `user_role` enum stays — small, stable, referenced by a function.

**A single `profiles.role` is not sufficient.** In Buntharik a rider orders food
and a restaurant owner orders food, so a one-role column would strip their
customer capability. Recommended `user_roles` with `CUSTOMER` implicit, plus
`restaurant_members` as the real merchant boundary. Not applied here because
deprecating `profiles.role` needs a `RolesGuard` code change — recorded as
DBQ-002 (D0).

**Declining to design promotions.** BQ-030 (who funds a discount) is `OPEN`, and
without a funder the ledger cannot balance a discounted order. Designing the
tables anyway would have meant guessing the business rule in schema form. Same
reasoning rejected a partial unique index enforcing one delivery per rider —
BQ-021 is open, and a configurable service check is reversible where a unique
index is not.

**No rider location history.** 🔴 Q-012 is unanswered. Latest position only, on
a separate `rider_availability` row so the highest-churn write in the system
stays off the identity table. The cheapest engineering choice and the lowest
legal risk agree here.

No migration file. No SQL executed. No `supabase db push`. No table, index, RLS
policy, trigger or function created. No business decision touched; no `Q`,
