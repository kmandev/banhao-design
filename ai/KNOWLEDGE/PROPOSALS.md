# Proposals

Ideas from an AI agent or developer that have **not** been approved. A proposal is never a decision — it only becomes one when a human/product-owner accepts it and it gets logged in `docs/DECISIONS.md` with `Status: ACCEPTED`.

All proposals below were generated by the 2026-08-09 architecture research pass (`ai/RESEARCH/`). **None is a technology decision.** Each is a recommendation for the Product Owner to accept, reject, or modify — see `ai/RESEARCH/HUMAN_DECISION_SHEET.md`.

## PROP-001

```yaml
id: PROP-001
type: PROPOSAL
status: PROPOSED
date: 2026-08-09
source: ai/RESEARCH/ARCHITECTURE_PATTERN.md
confidence: MEDIUM
owner: PRODUCT_OWNER
```

### Proposal

Adopt a **Modular Monolith** as the backend architecture pattern for Stage 1 and Stage 2, with clean internal module boundaries (Order, Payment, Merchant, Driver, Notification) that keep a later split into services possible.

### Why

CON-001 and CON-003 — the two hardest non-negotiable rules in the project — are both about transactional correctness between Order, Payment, and Ledger. A monolith gets this from a single database transaction; a microservices split would require distributed-transaction patterns (sagas/outbox) to achieve the same guarantee. Stage 1/2 volumes (`ai/RESEARCH/SCALE_MODEL.md`) present no scaling problem that microservices would solve.

### Pros

- Transactional integrity for money-related operations comes free from the database.
- Lowest operational complexity for a small, AI-assisted team.
- Splitting out a module later is far easier than merging services back together.

### Cons

- No failure isolation between modules.
- Requires ongoing discipline to keep module boundaries clean.
- Scaling is all-or-nothing until a module is deliberately extracted.

### Risks

Undisciplined implementation degrades into an unmodular monolith, making the "split later" escape hatch progressively more expensive. Mitigation: enforce boundaries structurally (no cross-module database access) from the first commit.

### Awaiting Decision

Product Owner. Related: Q-006 (backend stack — pattern and stack are separable decisions, but interact).

## PROP-002

```yaml
id: PROP-002
type: PROPOSAL
status: PROPOSED
date: 2026-08-09
source: ai/RESEARCH/REPOSITORY_STRATEGY.md; ai/RESEARCH/MULTI_APP_ARCHITECTURE.md
confidence: MEDIUM
owner: PRODUCT_OWNER
```

### Proposal

Keep **one repository** (this one), formalized as a monorepo with a shared package for API/domain types once application code begins.

### Why

`docs/AI_CONTEXT.md` already establishes this repository as the single source of truth, and the entire AI Memory System assumes one shared repository. Separately, REQ-002/CON-001 require all four clients to agree on the same Order/Payment state values — a shared types package makes that a compile-time guarantee rather than a process guarantee.

### Pros

- Preserves the existing single-source-of-truth model and AI Memory System without cross-repo tooling.
- Shared state-machine definitions cannot silently drift between clients.
- One PR can span a code change and the doc update `CONTRIBUTING.md` requires.

### Cons

- Repository grows large; CI needs scoping/caching to stay fast.
- Monorepo tooling has its own learning curve.
- If Driver App is Flutter (Dart) while other surfaces are TypeScript, "shared types" spans a language boundary and needs code generation rather than direct imports.

### Risks

Low. The main risk is CI slowness at scale, which is a solvable tooling problem rather than an architectural dead end.

### Awaiting Decision

Product Owner. Related: Q-016 (team/mobile framework constraints).

## PROP-003

```yaml
id: PROP-003
type: PROPOSAL
status: PROPOSED
date: 2026-08-09
source: ai/RESEARCH/REALTIME.md
confidence: MEDIUM
owner: PRODUCT_OWNER
```

### Proposal

Use a **layered real-time approach** rather than one mechanism: in-app live updates (WebSocket or SSE) for Merchant Kanban / Admin Live Map / Customer tracking; OS push notifications for closed-app alerts; and polling as an initial implementation and permanent fallback.

### Why

The requirements genuinely differ by surface. Push notifications cannot drive a live-updating map; in-app connections cannot reach a closed app. Polling is legitimate to ship first at Stage 1 volumes and upgrade later.

### Pros

- Each mechanism used where it actually fits.
- Allows shipping polling first, deferring real-time complexity until it's warranted.

### Cons

- Three mechanisms to build and maintain rather than one.
- WebSocket across multiple backend instances requires a shared pub/sub layer (e.g. Redis).

### Risks

Shipping polling first and never upgrading, leaving the Merchant "visible from 2 meters" requirement under-served. Mitigation: treat the upgrade as a tracked task, not an implicit intention.

### Awaiting Decision

Product Owner (or delegated to engineering — this is closer to an implementation choice than a product decision). Related: Q-006.

## PROP-004

```yaml
id: PROP-004
type: PROPOSAL
status: PROPOSED
date: 2026-08-09
source: ai/RESEARCH/QUEUE_ARCHITECTURE.md
confidence: MEDIUM
owner: PRODUCT_OWNER
```

### Proposal

Use a **database-backed or Redis-backed queue** for background jobs, rather than introducing a dedicated message broker at this stage.

### Why

The jobs that most need durability (payment webhook processing, settlement) also benefit most from a database-backed queue's ability to enqueue work in the same transaction as the data change — avoiding a class of bug where one commits and the other doesn't. A dedicated broker solves throughput and multi-service routing problems BANHAO does not yet have.

### Pros

- No additional infrastructure component beyond what's already needed.
- Transactional enqueue improves correctness for money-related jobs specifically.

### Cons

- Lower throughput ceiling than a dedicated broker.
- Fewer built-in routing/retry features (though most framework libraries provide retry/backoff).

### Risks

Throughput becomes a bottleneck at Stage 3+. Mitigation: revisit at that point; migration to a broker is a contained change if job dispatch is abstracted.

### Awaiting Decision

Product Owner (or delegated to engineering). Related: Q-006, Q-007.

## PROP-005

```yaml
id: PROP-005
type: PROPOSAL
status: PROPOSED
date: 2026-08-09
source: ai/RESEARCH/AUTHENTICATION.md
confidence: LOW
owner: PRODUCT_OWNER
```

### Proposal

Differentiate authentication by role: **Phone + OTP** for Customer and Driver (matching the existing designed flow), **Email + Password with 2FA or Phone + OTP** for Merchant, and **the strongest available option (passkeys, or password + mandatory 2FA)** for Admin.

### Why

Admin accounts can access reconciliation data, the approval queue, and live location data for every driver — the highest-value target in the system, with the smallest and most trainable user base, making stronger authentication cheapest to adopt there. Customer/Driver phone-OTP is already the designed UX.

### Pros

- Security effort concentrated where impact is highest.
- Customer flow requires no design change.

### Cons

- Multiple authentication paths to build and maintain.
- Merchant approach is genuinely undetermined — no Merchant login screen exists in the design yet.

### Risks

Confidence is marked LOW specifically because the Merchant and Admin recommendations have no design evidence behind them — they are reasoned from role sensitivity, not from anything BANHAO has documented.

### Awaiting Decision

Product Owner. Related: Q-014 (authorization granularity), and the SMS-provider cost input in `ai/RESEARCH/NOTIFICATIONS.md`.
